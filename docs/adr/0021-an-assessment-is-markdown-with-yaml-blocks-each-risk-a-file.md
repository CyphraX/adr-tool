# An Assessment is Markdown with YAML blocks, each Risk a file of its own

The Assessment module keeps two kinds of things a person writes, and both have to read well where Priya reads them — on GitHub, in a browser, without the suite ([personas.md](../personas.md)) — while the suite reads their structure, checks their Traces and writes into them without changing a byte it was not asked to ([ADR-0002](0002-never-reserialize-markdown.md)). An **Assessment** is a document of prose: a consultant's judgement, written over two weeks, with the Quality Scenarios it rates and the Findings it records standing in it. **Risks** and **Technical Debt Items** are registers of entries: each with a state that changes over months, recorded and changed by several people on several branches, outliving the Assessment that first named it.

So an Assessment is a Markdown file under `docs/architecture/assessments/`, with frontmatter for what the document as a whole is — its `date`, `status`, `authors`, `scope`, `previous` — and its title as its first `# ` heading, as an ADR has them ([ADR-0003](0003-on-disk-contract.md)). Each Quality Scenario and each Finding is an **entry**: a heading of the author's, followed by a small fenced YAML block whose key `scenario` or `finding` says what it is and gives its ID, with the keys the suite reads below — the six parts of a scenario, its quality attribute of ISO/IEC 25010, importance, difficulty and rating; the Scenarios a Finding concerns and its evidence. The text after the block, up to the next heading of its level, is the entry's own: the reasons for a rating, the judgement of a Finding. Everything else in the document is the author's, its sections and their headings among them, in whatever language. A piece of evidence names a Violation by its fingerprint as keys, as an Exception does ([ADR-0017](0017-rules-and-exceptions-share-one-file-keyed-by-fingerprint.md)), and every other thing by its ID; it is recorded on the Finding alone ([ADR-0009](0009-traces-are-recorded-on-the-source-only-unlike-back.md)).

The **Snapshot** of an Assessment is a YAML file beside it, `<ID>.snapshot.yml`, written as a whole by the suite: the commit, the day, and per Component a mapping of metric names to numbers — with room for the values inside a Source File, per function and per class, that part 13 measures. It is the one place of this module where derived data enters the repository, on purpose, as the SVG beside a Diagram is that of Diagrams ([ADR-0018](0018-a-diagram-is-a-yaml-file-and-its-svg-is-committed-beside-it.md)).

**Each Risk and each Technical Debt Item is a Markdown file of its own**, in `docs/architecture/risks/` and `docs/architecture/debt/`: frontmatter with its `state`, the days it was recorded and last changed, its `owner` and the `components` it concerns, its title as `# `, and its description below. The directories are set in `.arch/config.yml` as `assessments`, `risks` and `debt` ([configuration.md](../configuration.md)). The contract is [assessment-format.md](../assessment-format.md).

## Considered Options

- **Everything the suite reads in the frontmatter**, the Scenarios and Findings as lists of mappings at the top. One YAML document, the easiest to parse and to splice. But GitHub shows a frontmatter as a table above the text, so the ratings and the judgements would stand a screen apart, and a Finding's judgement would be a YAML string or would lose its place beside its evidence.
- **Labelled lines in Markdown**, `- **Stimulus:** …` under each heading. The best reading of all, and no code block in the document. But it is a grammar of its own — English labels in a German document, Markdown inside a value, a label that a person spells differently —, and a splice would have to know where a value ends. A YAML block is read and written by the same library that reads every other file of the suite, its ranges let the suite change one value where it stands, and GitHub shows it as code that a reader takes in at a glance.
- **The data in HTML comments**, invisible on GitHub. The reader would see a heading and a judgement, and never the rating or the evidence it rests on — what Priya most wants to see.
- **An Assessment as a YAML file**, prose in block scalars. One format for the suite, and a document nobody wants to write: no Markdown rendered on GitHub, indentation to keep in every paragraph.
- **The Snapshot as a section of the Assessment**, a Markdown table or a YAML block at its end. It would be in the one file the vision speaks of. But it grows with every Component and, from part 13, with every function of the code — thousands of lines in a 40-module system —, the numbers would drown the judgement in the diff and in the reading, and every Take a Snapshot and every Rename would rewrite the person's document. Beside it, the Snapshot is one file that changes as a whole and is read as data, as the SVG of a Diagram is.
- **One register file per kind**, `risks.md` with a section per Risk. One page that reads as a register. But two people who record a Risk on two branches both append at the end of the file and meet in a conflict, numbered IDs collide across branches, and every change of a state is a change of the one file everyone else changes too. A file per entry merges as Replies do ([review-format.md](../review-format.md), section 1); the register as one page is what the window (part 11), the report (part 12) and the eleventh chapter of arc42 (part 16) show, computed.
- **The fingerprint as its line of text**, `web-through-cart: web -> catalog`, as `adr check` prints it. A reader could copy it from the output. But in YAML the colon and blank inside it need quotes, which a person forgets, and a separator is a grammar of its own: ADR-0017 chose keys for the same reason.

## Consequences

- The suite reads an entry only from its block, never from the section it stands in or the words of its heading. A block written without a heading above it, or with both keys, is a Problem; a YAML block without either key is the author's code and is left alone.
- A new entry has to go somewhere in a document the suite does not own: after the last entry of its kind, the first Scenario before the Findings, the first Finding at the end, each first one under a level-2 heading the suite writes in English. The person moves it where it belongs; the suite finds it there.
- Writing into a block splices, as writing into the frontmatter of an Annotation does: a value replaced where it stands, a key inserted in the order of its table, an item appended to `evidence` in block style. A block written in a way a splice cannot serve — a mapping in braces, an alias — is changed in an editor.
- A final Assessment is a record: its Violations are not checked against the code of later days, and its metric values are read from its Snapshot, which is not taken again. A draft's Violations are checked, so that a Finding citing a Violation that is gone is seen before the Assessment is finished. The Snapshot makes "reads the same" a property of the files, not of the suite's memory.
- Rename of a Component rewrites the Components of `scope`, of the Risks and Technical Debt Items, of the evidence and of every Snapshot's keys, in the one change set of the Rename. The more Assessments a repository keeps, the more files one Rename touches; that is the price of each file reading on its own ([ADR-0009](0009-traces-are-recorded-on-the-source-only-unlike-back.md)).
- `assessment` is a module core as [ADR-0006](0006-one-core-package-per-module-on-a-shared-kernel.md) has them: on the kernel and `@adr-tool/structure/model` alone. It is told what exists elsewhere — the Violations, the Annotations, the ADRs — by its caller, and checks the Traces against that.
- The registers have no order but that of their IDs, which begin with the day an entry was recorded. Where a register is read as one list — a board by state, a chapter of arc42 —, it is computed.
